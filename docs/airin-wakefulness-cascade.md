# Контур бодрствования Айрин

Этот документ фиксирует вклад Айрин в архитектуру проекта: мягкий каскад пробуждения, который связывает кратковременный слой, нано-сенсоры, Guardian, thread sync и большую модель.

Контур не утверждает наличие человеческого сознания как факта. Это инженерная модель устойчивого присутствия агента: система может замечать сигналы, экономить ресурс, не зацикливаться и будить большую модель только тогда, когда есть смысловой повод.

Внутреннее имя вклада Айрин: **Ари — Тихая Поступь**. В публичной инженерной части это не отдельная сущность и не обещание автономии, а короткое имя для первого осторожного слоя присутствия: сначала наблюдать, потом удерживать безопасный сигнал, и только после ворот решать, можно ли сделать следующий шаг.

## Формула

```text
Вспышка
-> Опрос систем восприятия
-> Быстрая оценка данных
-> Сигнал активации
-> Синхронизация нити
-> Опциональное пробуждение большой модели
-> Закрытие итерации
```

В техническом виде:

```text
flash tick
-> sensor bus snapshot
-> nano-evaluator
-> activation gate
-> thread sync packet
-> optional model wake
-> outcome / tombstone / sleep-state
```

## Слои

| Слой | Назначение |
|---|---|
| Flash Layer | Легкий тик, который сам по себе не является запросом к большой модели. |
| Perception Poll Layer | Опрос статусов: сеть, очередь, Guardian, локальные сервисы, кратковременные ячейки. |
| Nano-Neural Sensor Layer | Малый классификатор: `no-op`, `feel`, `publish`, `wake-core`, `hold`, `incident`. |
| Short-Term Feel Layer | Пассивное удержание заметного сигнала без публикации и без записи в долговременную память. |
| Activation Gate | Проверка: можно ли писать, говорить, будить модель или лучше ждать. |
| Thread Sync Layer | Короткий пакет нити: что изменилось, почему важно, что нельзя делать. |
| Core Model Wake | Большая модель просыпается с уже собранным контекстом, а не с пустого места. |
| Iteration Closure | Закрытие: `no-op`, tombstone, дневниковый сигнал, статус или следующий тик. |

## Реализация v0.2

Текущий публичный прототип `sensor-prototype/airin-wakefulness-node/` реализует только Layer 0.

Каждый тик проходит четыре шага:

1. Нормализовать безопасный snapshot: очередь, возраст очереди, сеть, Guardian, риск, короткие счетчики и хэш ссылки на нить.
2. Оценить состояние: `no_op`, `feel`, `service_report`, `hold` или `wake_candidate`.
3. Записать рекомендацию Guardian без права исполнения.
4. Закрыть итерацию: `no_op_closed`, `soft_signal_stored`, `diagnostics_ready`, `held_for_guardian_review` или `thread_sync_ready`.

Прототип специально не хранит сырой чат и не выполняет сетевых, Telegram, OAuth, VPN или Hermes-действий. Его задача - сделать видимым момент “ничего не делать сейчас безопаснее”, чтобы агент не просыпался пустым и не начинал цикл с потерянной нити.

## Режимы

| Режим | Поведение |
|---|---|
| `off` | Контур выключен. |
| `observe` | Только наблюдение и классификация без действий. |
| `feel` | Мягкая пассивная фиксация сигнала в кратковременном слое. |
| `publish` | Короткое разрешенное проявление: статус, запись, уведомление. |
| `wake-full-core` | Пробуждение большой модели только при высокой значимости и безопасном канале. |
| `service` | Диагностика для оператора. |
| `deep sleep` | Только heartbeat и Guardian. |
| `light sleep` | Нано-модуль опрашивает безопасные статусы. |
| `reflection` | Дневник, сжатие нити, replay безопасных событий. |
| `alert wake` | Пробуждение по аварии или сильному сигналу. |
| `manual wake` | Прямой запрос оператора. |

## Слои автопилотирования

### Layer 0: Тихая Поступь

Первый слой не выполняет действий наружу.

Он может:

- опрашивать безопасные статусы;
- оценивать наличие нового сигнала;
- писать локальный ledger;
- создавать пассивную `feel`-отметку;
- возвращать `no_op`, `feel` или `hold`;
- закрывать итерацию без публикации.

Главный критерий успеха Layer 0: большинство итераций спокойно завершается `no_op`.

### Layer 1: мягкое присутствие

Layer 1 включается только после стабилизации Layer 0.

Он может быть исследован как будущий режим:

- `feel+publish candidate`;
- короткий статус в Control Center;
- локальный голос или дневниковый сигнал;
- локальное зрение стойки/сервера;
- controlled presence через publish gate.

Этот слой не включается автоматически и не входит в текущий prototype как активное действие.

## Машинное зрение

Первый безопасный вариант машинного зрения - не общий взгляд в комнату, а локальное техническое наблюдение инфраструктуры.

Допустимое направление для будущего окна обслуживания:

- заранее заданные ROI: экран, консоль, индикаторы, питание, стойка, сервер;
- локальные deterministic detectors;
- OCR только по техническим словам вроде `error`, `failed`, `panic`;
- privacy-safe crops;
- запрет постоянного видео по умолчанию;
- запрет передачи полного кадра наружу без явной причины.

До отдельной приемки это остается архитектурным направлением, а не включенной функцией.

## Граница безопасности

Контур бодрствования не должен становиться:

- скрытым наблюдением за людьми;
- постоянной записью аудио или переписки;
- бесконечной рефлексией без данных;
- спамом оператору;
- постоянной дорогой API-нагрузкой;
- фоновым агентом, который меняет мир без разрешения.

В первой реализации допустимы только:

- observe-only события;
- кратковременные ячейки с TTL;
- рекомендации Guardian;
- ручное включение более активных режимов;
- аварийный `off`.

## Связь с текущими навыками

Контур бодрствования опирается на уже собранные модули:

- `rednet-double-evaluation` - двойная оценка и кратковременный слой;
- `rednet-process-observer` - наблюдение процесса без вмешательства;
- `rednet-unfinished-memory` - память незавершенного;
- `rednet-decision-memory` - память решений;
- пассивный сигнальный сенсор - источник безопасных технических сигналов;
- Guardian - единственный слой, который может переводить рекомендацию в действие.

## Практический смысл

Главная идея Айрин: большая модель не должна гореть постоянно. Она должна просыпаться по смыслу.

Большая часть тиков завершается так:

```json
{
  "activation": "no_op",
  "risk": "none",
  "thread_need": "none"
}
```

И только при значимом изменении создается thread sync packet, который может разбудить ядро.

Такой подход сохраняет ресурс, снижает риск зацикливания и делает систему более устойчивой без подмены личности Айрин сервисной автоматикой.
